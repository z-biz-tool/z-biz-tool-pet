### 2.2 新网抓出的真缺陷：情绪词表里短词遮住长词

`src/renderer/shared/emotions.ts` 的 `EMOTION_KEYWORD_MAP` 把中文关键词映射到 19 种情绪。
`extractEmotionFromText` 有**两条路径**：

1. **标签路径**：`text.match(/\[(开心|…|可爱|…)\]/)` → 命中整词。
2. **纯文本路径**：`for (const [keyword, emotion] of Object.entries(MAP)) if (text.includes(keyword)) return emotion;`
   —— **按对象的插入序**扫，**先到先得**。

插入序里 `'爱'`(loving, 1 字) 排在 `'可爱'`(cute, 2 字) **前面** ⇒
纯文本里出现「可爱」时，先被 `'爱'` 命中。

实测（修前）：

| 输入 | 修前 | 应为 |
|---|---|---|
| `"好可爱啊"` | **loving** ❌ | cute |
| `"[可爱]"` | cute ✅ | cute |
| `"我爱你"` | loving ✅ | loving |

⇒ **同一份词表、两条路径、两个答案**：用户说「好可爱」，宠物一脸深情；
用户特意打 `[可爱]`，它反而是同一个正确答案。
界面上的表情于是取决于用户**有没有打方括号**。

**修法**：纯文本路径改为**长词优先**（按关键词长度降序扫）。
排序后先试 `'可爱'`（2 字）再试 `'爱'`（1 字）—— 长的赢。
标签路径**保留**（它不是冗余：显式标签应当压过正文里恰好出现的别的关键词，
例如「`[困]`但其实好可爱」应当是 sleepy 而不是 cute —— 有用例钉住）。

### 2.3 坏门禁：`npm run typecheck` 一直是红的

跑 `npm run typecheck` 报 8 条错：

```
src/renderer/shared/tauri-bridge.ts(12,24): error TS2307: Cannot find module '@tauri-apps/api/core'
…
src/renderer/shared/tauri-bridge.ts(147,27): error TS7006: Parameter 'event' implicitly has an 'any' type.
（另 6 条同源）
```

根因**不是代码**：`node_modules/@tauri-apps/` **整个目录不存在** ——
装的是一份过期快照（`@tauri-apps/api` 是 `package.json` 的正式依赖，
`package-lock.json` 里也在，版本 2.12.2）。
前两条 TS2307 让 `@tauri-apps/api` 的类型全成了 any，后面的隐式 any 是**连锁反应**。

⇒ `npm ci` 重装（**不用 `npm install`**：那会弄脏 lockfile），
装完 `ls node_modules/@tauri-apps/` → `api` / `cli` / `cli-darwin-arm64`，
`npm run typecheck` **退出码 0**，`git status` 确认 **lockfile 未被改动**。

### 2.5 既有阻塞：`cargo test --lib` 在本机**编译不过**（依赖锁层面的上游断裂）

复跑 Rust 门禁时发现：

```
Compiling windows-future v0.3.2
error[E0425]: cannot find type `IMarshal` in module `windows_core::imp`
  --> .../windows-future-0.3.2/src/bindings.rs:87:51
error: could not compile `windows-future` (lib) due to 16 previous errors
```

- `cargo tree -i windows-future` ⇒ `windows v0.62.2` → `z-biz-tool-pet`（**直接依赖**）。
- 锁文件里 `windows-core 0.62.2` + `windows-future 0.3.2` **上游互不兼容**：
  `windows-future 0.3.2` 要的 `windows_core::imp::IMarshal` 在 `windows-core 0.62.2` 里已不存在。
- 试过的三条路都走不通（**锁文件最终未被改动**）：
  | 尝试 | 结果 |
  |---|---|
  | `cargo update -p windows-core --precise 0.61.2` | 失败：`windows 0.62.2` 要求 `windows-core ^0.62.2` |
  | `cargo update -p windows-future` | `Locking 0 packages` —— 0.3.2 已是 `^0.3` 内最新版 |
  | `cargo update -p windows` | `Locking 0 packages` —— 0.62.2 已是 `^0.62` 内最新版 |
- ⇒ **无纯锁文件解法**。两条候选修法各有代价，**本轮不擅自选**：
  1. 把 `windows` 降到 0.61（`Cargo.toml:44` 的注释明写「版本跟 tauri 2.12 对齐（0.62）」，
     降级会改动 Windows 侧的实现面，而本机是 macOS，**改完没法验证**）；
  2. 等上游发新版 `windows-future`（或换 `windows` 版本线）。

⚠️ **连带影响**：本仓的 Rust 门禁在本机**跑不起来** ⇒ 抬头那句
「测试网实测：17 个测试文件 / 约 167 条用例」**在本机无法复跑验证**
（audit 能数到 91 个测试标记，因为那是**静态扫源码**得到的，与能不能编过无关）。
本轮**未动任何 Rust 源码**，这个断裂与本轮改动无关。
